# mesync 决策记录规则

本文件定义「什么情况下该记录决策，以及如何记录」。它是决策链（DecisionGraph）的客观规范。

## 一、什么算「有意义的决策」

只有满足下面任一条件，才值得记录为一个决策节点：

1. **方案取舍**：用户在多个方案之间做了选择，或明确否掉了某个方案。
2. **反复磨合**：同一个功能 / 文件 / 写法被来回调整多次后，最终确定了一个做法（说明背后有隐含的取舍）。
3. **技术/架构决策**：选型、架构分层、数据流设计、引入/移除依赖等会影响后续开发方向的决定。
4. **约束与约定**：确定了一条会约束后续代码的规则、约定或边界（如「统一用 X 而不是 Y」）。
5. **显式要求**：用户明确说「记住这个」「记下这个做法」等。

## 二、什么「不算」决策（不要记录）

- 小改动：换方法名、移动代码位置、改注释、格式化。
- 无争议的常规实现：照着既有模式写，没有「选择」的空间。
- 一次性、不产生后续影响的操作。
- 用户随口一提、尚未确定的意向（这类属于「待定」，除非用户明确拍板）。

**原则：宁缺毋滥。** 不确定时，不记录。

## 三、决策节点字段规范

记录决策时，各字段按如下填写：

| 字段 | 说明 | 要求 |
|------|------|------|
| `decision` | 做了什么决定 | 一句话说清，具体到「定了什么」 |
| `rationale` | 为什么这么做 | 核心理由，说清「因为什么」 |
| `trigger` | 什么触发了这个决策 | 可空；如「用户反馈 bug」「性能不达标」 |
| `alternatives` | 被否掉的备选方案 | 数组，每项含 `option`（方案名）+ `why_not`（为什么否掉） |
| `taste_signals` | 这个决策反映的品味偏好 | 数组，每项含 `signal`（偏好名）+ `context`（如何体现） |
| `outcome` | 结果 | `adopted`（采纳，默认）/ `reverted`（已回退）/ `refined`（已修正）/ `pending`（待定） |
| `caused_by` | 因果链：这个决策的直接前因 | 前一个决策节点的 id，可空 |
| `supersedes` | 推翻/取代了哪个旧决策 | 被取代的旧决策节点 id，可空 |

## 四、因果链关联

决策之间可以形成「因果链」。**关键：同一件事的持续讨论，不是「覆盖」旧决策，而是「追加」新节点、串联起来。** 对话是连续的，一个话题会反复讨论、逐步演进，后面的讨论会修改前面的结论——每次迭代都追加一个新决策节点，用下面的字段把链路连起来，让「这个话题是怎么一步步演进的」可追溯。

- **caused_by**：当前决策是「因为」某个前序决策（或其暴露的问题）才产生的，就填那个决策的 id。
  - 例：先决定「用 A 框架」，后来 A 暴露性能问题，又决定「换 B 框架」——第二条决策的 `caused_by` 指向第一条。
- **supersedes**：当前决策「修改/取代」了某个旧决策的结论，就填旧决策的 id。
  - 例：把「用 A 框架」改成「用 B 框架」时，新决策的 `supersedes` 指向旧决策。
  - 同一话题的反复讨论中，后面一轮的共识如果改动了前面一轮的结论，也用 `supersedes` 关联；同时把被取代的旧决策的 `outcome` 更新为 `refined`（已修正）或 `reverted`（已推翻）。

**注意**：`caused_by`（前因）和 `supersedes`（取代）不必强行同时填。两者语义不同：`caused_by` 强调「因果」，`supersedes` 强调「取代/修改」。只有在关系明确时才填，不要为了「链而链」。
