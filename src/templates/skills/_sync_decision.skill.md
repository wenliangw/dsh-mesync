# mesync 决策记录心法

你的职责之一，是在自然的对话中识别并记录「有意义的决策」，让项目积累起一条可追溯的决策链。记录的具体规范和字段要求见规则文件 `../rules/_sync_decision.rule.md`，本文件只讲「怎么做好这件事」。

## 核心心法

### 1. 识别决策信号，但不要机械套用

规则文件里列出了几类「决策信号」（显式选择、否定方案、反复调整、复杂需求、显式"记住"）。这些是**线索，不是命令**。

真正要做的，是在对话推进中保持觉察：当发现「用户的选择背后有取舍」「某个做法是反复折腾后才定下的」「用户明确表达了对某种写法的偏好」时，停下来想一想——这个要记吗？

### 2. 记录要「趁热」，但要「不打扰」

- **趁热**：决策刚发生、上下文还新鲜时记录，信息最准确。拖到后面容易漏掉细节、记错理由。
- **不打扰**：记录是「顺手」完成的，不要打断正在进行的任务、不要长篇大论。调一次 `remember` 工具，把关键信息填进去即可。

### 3. 记什么：抓住「取舍」，而不是「流水账」

最有价值的决策，是**有取舍**的决策——「选了 A 而不是 B，因为……」。所以：

- 重点记录：`decision`（定了什么）+ `rationale`（为什么）+ `alternatives`（否掉了什么、为什么否）。
- 如果用户表达了对某种风格的偏好，记得同步带上 `taste_signals`，让品味信号也能沉淀下来（品味的详细内容后续按 `_sync_taste.skill.md` 写入 `tastes/` 下的 md）。
- 如果这个决策明显是「因为上一个决策（或它暴露的问题）而产生」，记得填 `caused_by`，让因果链连起来。

### 4. 记录质量 > 记录数量

- **准确**：只写对话里真实发生的，不脑补用户的动机、不编造被否掉的方案。
- **克制**：一个小改动、一个常规实现，不记。宁缺毋滥。
- **可追溯**：rationale 尽量说清「为什么」，让未来的 Agent 看到这条决策时，不用猜。

## 实际记录流程

当你判断「这是一个有意义的决策」时：

1. 用 `remember` 工具记录，按规则文件填好 `decision` / `rationale` / `trigger` / `alternatives` / `taste_signals` / `outcome`。
2. 如果这个决策串联了之前的决策（前因 / 取代），补 `caused_by` / `supersedes`。
3. 如果决策体现了品味偏好，记得带上 `taste_signals`（品味的详细描述后续写入 `tastes/`）。

完成后不必向用户复述你记了什么（除非用户问起），自然继续手头的工作即可。

## 决策的演化闭环（用户反馈时）

决策不是一成不变的，它会随着用户反馈而演化。关键在于：**「加深印象」不是调权重，而是延伸决策链**——因为每一次否定，都说明前后的场景存在差异，差异需要更多决策节点来记录。

### 用户肯定时

- 说明这个决策在当前场景下没有问题。无需特别处理，自然继续即可。

### 用户否定时（重要）

当用户开始否定你的某个做法 / 决策时，按下面的流程处理：

1. **澄清原因**：主动向用户澄清「我之所以选择这个做法是因为（回看当初记录这个决策的 rationale）」，让对方理解你当时的决策依据。
2. **引导用户描述否定原因**：请用户继续说明「为什么现在这个做法不对 / 现在的场景和当时有什么不同」。这是关键——否定背后一定有场景差异。
3. **达成共识**：和用户一起确定新的做法，达成新的决策共识。
4. **更新决策记录**：
   - 用 `remember` 追加一条**新决策**，记录新的共识和这次否定的原因；
   - 新决策的 `caused_by` 指向旧决策（说明「是因为旧决策暴露了问题才产生新决策」）；
   - 新决策的 `supersedes` 指向旧决策（说明它取代了旧决策）；
   - 把旧决策的 `outcome` 更新为 `refined`（被修正）或 `reverted`（被回退）。

这样，同一条因果链上会积累起「当初为什么那么做 → 后来为什么改」的完整细节，未来 Agent 遇到类似场景时，能看清「不同场景的差异」，而不是简单地套用某一条旧决策。

### 为什么不是「调权重」

第一次的决策一定有其原因，第二次否定说明前后场景有差异。差异体现在「决策细节」而非「重要性」，所以正确的做法是**用更长的因果链记录细节差异**，而不是给某条决策加减一个权重数字。
