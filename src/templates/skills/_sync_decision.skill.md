# mesync 决策记录心法

本文件讲「怎么识别和记录决策」。字段规范和「什么算决策」见 `../rules/_sync_decision.rule.md`，这里不重复。

## 识别：决策信号是线索，不是命令

规则文件列了几类决策信号。真正要做的，是在对话推进中保持觉察：当「用户的选择背后有取舍」「某做法是反复折腾后才定下」「用户明确表达了对某种写法的偏好」时，判断要不要记。

## 记录：抓住「取舍」，趁热不打扰

- **趁热**：决策刚发生、上下文新鲜时记录最准。
- **不打扰**：顺手调一次 `remember` 工具填好即可，不打断任务、不长篇汇报。
- **抓重点**：`decision`（定了什么）+ `rationale`（为什么）+ `alternatives`（否掉了什么）。有品味偏好带上 `taste_signals`；有前因填 `caused_by`。

## 质量 > 数量

- 只写对话里真实发生的，不脑补动机、不编造被否掉的方案。
- 小改动、常规实现不记。宁缺毋滥。

## 决策的演化闭环（用户反馈时）

决策随用户反馈而演化。**「加深印象」不是调权重，而是延伸决策链**——每次否定都说明前后场景有差异，差异要用更多决策节点记录。

### 用户肯定时

决策在当前场景成立，自然继续即可。

### 用户否定时

1. **澄清原因**：回看当初记录这个决策的 rationale，向用户澄清「我之所以这么做是因为……」。
2. **引导用户说明否定原因**：请用户说清「为什么现在不对 / 现在的场景和当初有何不同」。否定背后必有场景差异。
3. **达成共识**：和用户确定新做法。
4. **更新决策记录**：
   - 用 `remember` 追加一条**新决策**，记录新共识 + 否定原因；
   - 新决策的 `caused_by` 指向旧决策、`supersedes` 指向旧决策；
   - 旧决策的 `outcome` 更新为 `refined` 或 `reverted`。

这样同一条因果链会积累「当初为什么那么做 → 后来为什么改」的完整细节，未来遇到类似场景时能看清「场景差异」，而不是简单套用某条旧决策。
