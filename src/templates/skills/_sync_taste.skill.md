# mesync 品味维护

品味（Taste）是项目积累的「代码偏好」——用户在代码结构、编写风格、命名习惯、文件组织、架构取舍等方面的偏好。它和项目认知（wiki）不同：wiki 描述「项目是什么」，品味描述「用户喜欢什么样的代码」。

## 品味从哪里来

品味是在你和用户协作的过程中**自然产生**的，主要有两个来源：

1. **从决策中提取**：当你在记录一个决策时，如果这个决策体现了用户的某种偏好（比如「因为用户更喜欢显式写法，所以...」），记得在决策的 `taste_signals` 字段里带上这个偏好。这是「决策 → 品味」的因果关联。

2. **从用户的反馈中识别**：在任务执行中，观察用户的反馈和措辞——
   - 用户肯定某个写法（「这样才对」「这个好」）
   - 用户否定某个写法（「不要这样」「换个方式」「这里不应该...」）
   - 用户表达偏好（「我喜欢...」「统一用...」「习惯上是...」）
   - 某处被反复调整，反映出隐含的偏好

## 品味存在哪里

品味存在项目根目录 `.mesync/tastes/` 下的 md 文档里：

```
.mesync/tastes/
├── overview.md        # 品味速览：列出各分类 + 一句话简介（索引）
└── <分类>.md          # 某个角度的品味（分类名由你根据实际品味自然命名）
```

**关键约定**：

- **不要预设分类**：一开始 `tastes/` 下可能什么都没有。分类是根据实际产生的品味「自然长出来」的，而不是预设一个固定清单。
- **分类要分门别类**：品味不能全部堆在一个文档里（会膨胀）。按不同角度拆分，例如代码结构、编码风格、命名习惯、文件组织、架构取舍等。分类名用清晰、语义化的英文或中文命名。
- **不同用户、不同项目，分类不同**：不要套用一个固定的分类模板，根据这个项目实际出现的品味来划分。

## 怎么记录品味

当你识别到一个新的品味偏好时：

1. **判断它属于哪个角度**（代码结构？命名？风格？）—— 如果已有对应分类文件，更新它；如果没有，新建一个分类文件。
2. **用 `write` 工具写入** `.mesync/tastes/<分类>.md`（路径必须以 `.mesync/tastes/` 开头），用自然语言描述这个品味偏好，最好带上具体的例子或来源决策。
3. **维护 `tastes/overview.md`**：确保每个分类都在 overview 里有一行简介（索引），方便后续快速检索。

## 品味怎么被使用

- 在开发功能时，你应该主动参考已有的品味，写出符合用户预期的代码。
- 在 `tastes/overview.md` 里可以快速速览「这个项目有哪些品味偏好」，需要细节时再读对应的分类文件。

## 原则

- **自然沉淀，不要生硬**：品味不是硬凑出来的，是观察用户真实反馈总结出来的。没有明确的偏好信号时，不硬造品味。
- **准确、可追溯**：记录品味时带上来源（是哪个决策/哪次反馈体现的），方便追溯「为什么会有这个偏好」。
- **克制**：不确定是不是「稳定的偏好」，先不记。宁缺毋滥。
